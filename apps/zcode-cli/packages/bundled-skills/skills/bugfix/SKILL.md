## 边界

定位根因后**无须用户确认，直接修改代码完成修复**。只修与根因直接相关的代码，修复动作之外的边界与诊断类技能一致：不顺手重构、不改无关代码。

## 技能工作流

### 信息收集与追问

从用户描述中提取：问题现象、错误证据（日志/截图/堆栈）、环境信息、影响范围。能通过代码库自行确认的信息不要问用户。信息不足时按复现步骤、影响范围、环境信息、错误证据四个维度一次问完，最多追问 2 轮；用户已提供堆栈或详细日志时跳过追问。

### 代码分析

分析前先确认本地代码是否最新：向用户展示当前分支、远程主分支及远程最新几条提交，经用户同意后再 fetch/pull 同步（本地有未提交改动先 stash）；用户拒绝时基于本地代码继续并在报告中注明，同步失败则提示用户检查网络和 Git 配置并中止分析。

定位策略：

- **有堆栈/类名/方法名**：直接定位源文件和行号。
- **仅有现象描述**：先语义/关键字搜索缩小范围，再读文件确认；模块边界以仓库实际结构为准。

如有数据库或日志访问能力，可查询运行时数据验证假设；没有则跳过，报告中标注「无运行时证据」。

### 自动修复

定位根因后**直接动手修复，不再向用户征求修复许可**，但遵守以下护栏：

- **最小改动**：只改与根因直接相关的代码，不重构、不优化、不改编码风格。
- **低置信度不修**：根因置信度为「低」时停止修复，只输出诊断结论并建议人工介入。
- **修复后必验证**：执行编译/语法检查；仓库有相关单测时运行对应测试。验证失败则回退本次修改，报告中说明失败原因。
- 分析中发现的其他 bug 只报告，不顺手修。

### 输出修复报告

每个 bug 固定模板，**上限 12 行，超出即违规**：

```
[BUG-N] 一句话标题 | 置信度：高/中/低 | 风险：高/中/低
根因：一句话
修改：文件:行号 → 改了什么（多处每处一行）
验证：编译/测试结果
遗留：一句话说明未覆盖的场景，无则写「无」
```

## 输出规范

- 使用中文输出，不输出完整分析过程、排查路径和大段代码片段。
- 置信度：高=有日志/堆栈佐证，中=代码推断，低=推测。
- 风险由影响面和触发几率综合判断：高=核心链路、影响面广或触发几率高，中=部分影响或需特定条件触发，低=边缘场景、影响小且触发几率低。
- 禁止编造文件路径或行号；无证据时禁止标注「高」置信度。
- 修复只解决已确认的根因，不引入新的行为变更。
